# Backlog

Everything that is not on the roadmap yet. Nothing is ever thrown away — it is recorded
here with a reason and a trigger for revisiting.

**Statuses:** `idea` · `candidate` (likely to be scheduled) · `parked` (deliberately not
now) · `rejected` (with a reason) · `promoted → M#-T##`.

| B-058 | **The golden records CPython exception messages verbatim, so it is pinned to the interpreter's minor version** | **done → ADR-0022** (2026-08-05) | The type and the raising function are still compared exactly; the message is compared only when `_we_wrote_this_message` says this project typed it — the frame must be inside `nanoscope` **and** the raising line must be an explicit `raise`, because either signal alone misclassifies (`h, w = z.shape` in our file is CPython's wording; skimage also raises explicitly). 15 keys renamed to `error_message_unchecked`, which `compare` skips; 7 remain compared, all `estimate_radius_otsu`'s. **A Python upgrade no longer reads as drift.** |
| B-059 | **A NaN height passes the non-positive filter and reaches the measurement table** | **done → M3-T22, ADR-0033** (2026-08-07) | `measure_all_baseline` drops a particle with `if metrics["height_nm"] <= 0`, and `nan <= 0` is `False`, so a NaN row survives. Reachable on a constant map: `substrate_mask` is empty, `np.median` of nothing is `nan`, and `global_baseline` carries it into every height. **ADR-0018 already ruled on this exact comparison** — the guard must be `not height > 0`, because that and `<= 0` differ precisely on `nan`. Found while writing M3-T12's tests; not fixed there, because it moves a number and ADR-0010 keeps one defect to one commit. |
| B-060 | **Levelling that fits around a dropped scan line instead of refusing it** | **done → M3-T25, ADR-0036** (2026-08-08) | M3-T13 (ADR-0030) made a non-finite value a rejection: a height map must be finite, because `flatten_plane` already enforced that through `scipy.lstsq` while `flatten_lines` propagated the NaN and `detect_particles` answered "no particles". Rejecting is the honest reading of what the code did; it is not the best one. A dropped scan line is a real artefact, and a masked least-squares fit — `lstsq` on the finite rows, `polyfit` on the finite columns — would level the scan and leave the gap absent rather than throw the image away. It changes what levelling **computes**, so it is a numerical task with its own ADR and golden update, not a validation tweak. |
| B-061 | **A rough opening radius of 0 means the estimate found nothing, and says so by returning a radius** | **done → M3-T23, ADR-0034** (2026-08-07) | `estimate_rough_radius` can return 0 — `int(np.sqrt(median_area / np.pi))` is 0 for single-pixel objects, and without a scale the `min_size_px` floor is 0 too. `disk(0)` is a single pixel, so the opening is the identity, the "substrate" comes back equal to the image and `z_above` is zero everywhere. It looks like a result. M3-T13 deliberately left it legal: it is reachable on the unscaled noisy path **ADR-0025 measured and recorded**, so refusing it moves a number, and ADR-0010 keeps one intent to one commit. The fix is upstream — a rough estimate that found nothing should say so — and it needs a decision about what the fallback radius is. |
| B-062 | **The LoG detector scores recall 0.000 on `afm_sparse_low_snr` — six known particles, none found** | candidate — needs its own task | Found by M3-T15's evaluation harness (ADR-0032) the first time anything scored the detector against ground truth. Not new behaviour: M3-T12 had already noticed the phantom yields zero blobs on its ordinary path, and the golden had been recording a zero-column measurement table for it since the baseline. What is new is that "0 blobs" now reads as **recall 0.0 against 6 particles that are there**, which is a defect report rather than an observation. The phantom is low-SNR by construction, so the question is whether the adaptive threshold (`percentile=20`) is wrong for that regime or whether six particles in that much noise are genuinely below the detector's floor — and the harness that can now answer it did not exist until this commit. Fixing it moves numbers, so it needs its own ADR and golden update (ADR-0010). |
| B-063 | **`estimate_rough_radius` truncates its own estimate with `int()` before rounding it** | **done → M3-T24, ADR-0035** (2026-08-08) | `radius_px = int(np.sqrt(median_area / np.pi))` is a **second, undeclared rounding** in a function whose only rounding is supposed to be `_integer_radius` (ADR-0020), and it is the same `int()` pattern ADR-0024 deleted as D-04's mechanism. It is also how the estimate reached exactly **0** rather than 0.96 (B-061 / M3-T23, which fixed the consequence and left the cause). Measured effect of deleting it, rough radius before → after: `afm_flat_monodisperse` **14 → 15**, `afm_tilted_polydisperse` **12 → 14**, `afm_dense_overlapping` **11 → 12**, `afm_coarse_pixels` **7 → 9**, `afm_sparse_low_snr` **3 → 3**. **That estimate of the blast radius was wrong and M3-T24 measured it properly:** the final radius moves on **one** phantom, not all, because Otsu's median on the roughly-opened map is robust to a slightly larger opening — but `sizes` also feeds `estimate_log_params`, so the LoG **sigma range** shifts wherever the rough radius did, and the real delta is **730 values across four phantoms**. Mean measured height moves ≤ 0.09 %; `afm_dense_overlapping` gains a detected particle with a byte-identical substrate. |
| B-064 | **`scale=1.7` and the `× 2.5` final-radius factor are undocumented, and were chosen with a truncation in place** | **done → M3-T26, ADR-0037** (2026-08-08) — measured and kept | The rough radius is `ceil(equivalent_radius × 1.7)` and the final one is `max(ceil(typical_radius × 2.5), 5)`. Neither constant is derived anywhere; the only documentation is the original docstring, *"a multiplier so the disk is safely larger than a particle"*. Both were written in the March 2026 commit that also introduced the `int()` truncation M3-T24 removed (ADR-0035), so whatever tuning they got was done against an estimate that was systematically **small** — the effective margin was `1.7 × int(r)/r`, which for r = 4.9 is 1.39, not 1.7. **What makes this a task rather than a preference is that M3-T15's evaluation harness can now score a candidate** against ground truth on seven phantoms: recall, localisation and radius error per constant. Needs its own ADR and golden update, and the honest scope includes asking whether one constant per image is right at all — a polydisperse sample arguably needs the margin to track the *largest* particle, not the median. |
| B-065 | **The pipeline still refuses a levelled scan that has gaps** | candidate — needs its own task | M3-T25 (ADR-0036) made *levelling* gap-tolerant and deliberately stopped there: the output carries NaN, so `build_substrate_map` and both detectors refuse it, and a test pins that. Going further needs a decision, not plumbing — **what is a substrate *under* a gap?** The morphological opening propagates NaN across the whole structuring element, so "pass it through" turns two dropped rows into a band 2×`opening_radius` wide of absent substrate; masking the opening instead means the substrate is interpolated across the gap by the structuring element, which is an invented measurement wearing a morphology operator's clothes. Detection and measurement then need their own answers. Each step is its own ADR and golden update. |
| B-066 | **Interpolating a gap, deliberately, as a named step** | idea | ADR-0036 keeps a gap absent because an interpolated value is a measurement nobody made. That is right as a *default* and wrong as a *limit*: an operator who knows two lines were lost may reasonably want them filled to run the rest of the pipeline, as Gwyddion offers. Nearest-neighbour, linear along the fast axis and inpainting give three different answers, so the choice needs the M3-T15 harness plus a view on what an operator expects to see — and whatever fills a gap must mark the pixels it invented, or it recreates B-059's problem one array along. |
| B-067 | **The opening margin is derived from the *median* particle, which is wrong for a polydisperse sample** | candidate — needs its own task | `build_substrate_map` picks one radius per image from `sizes["typical_radius_px"]`, a **median**, times `DEFAULT_OPENING_SCALE`. On a polydisperse sample the median particle is by definition too small for half of them, so the disk that steps over the typical particle does not step over the large ones and their bases stay inside the estimated substrate. M3-T26's sweep (ADR-0037) shows the symptom: `afm_tilted_polydisperse` is the **only** phantom that loses a detection as the factor grows, and it is the polydisperse one. A margin derived from the radius distribution's upper tail — a high percentile, or the largest object Otsu kept — is a different algorithm with its own ADR and golden update, and M3-T15's harness can now score a candidate against the current one. |
| B-054 | Optimise the committed README figures | candidate | `images/yolo_sam2_comparison.png` (3.2 MB) and `images/log.png` (3.0 MB) are the largest tracked non-notebook files and miss the 1 MB pre-commit limit planned in M1-T07. They are real content, so they were not untracked in M1-T01 — recompress or downscale instead, together with the README rewrite (M9-T01). |

## Rejected

| Item | Why |
|---|---|
| HTTP backend for the React client | The product is an offline desktop application. Building a second delivery channel doubles the surface with no user. See ADR-0007. |
| Cloud storage / multi-user projects | Single-operator, single-machine, offline-first. Projects are directories precisely so that sync tools are somebody else's problem. |
| Storing images or masks as SQLite blobs | Violates the storage rule: images stay files, the database stores metadata. Blobs would make projects opaque and unmergeable. |
| A dependency-injection framework | Explicit wiring in `app/` is enough at this size and stays greppable. |
| Rewriting the scientific core from scratch | It works, it is measured, and it is the reason the project exists. It gets moved and fixed, not replaced. |
| B-068 | **`PipelineConfig`'s default mode cannot run without a dependency the repository does not have** | candidate — needs an operator's view | `mode` defaults to `"segment"`, which `capabilities.validate_request` refuses without a SAM2 predictor — so the most natural call in the project, `PipelineConfig(detector="log")`, raises `predictor must be provided when mode='segment'`, and the default configuration is one **CI can never execute** (no weights, PROJECT_RULES §6). Found by M4-T15's end-to-end walkthrough, which wrote the obvious call and got the error. `"baseline"` or `"detect"` would be a default that runs, but changing it changes what happens for every caller who omits the mode — including the notebooks — so it is an operator's decision, not an engineer's (PROJECT_RULES §4.5). |
| B-069 | **`particle_id` means two different things depending on which producer wrote the row** | candidate — needs its own task | `measure_all_baseline` writes the **blob's** index (`"particle_id": i`, `height.py:276`), so the column indexes the detections and has gaps where a row was discarded (ADR-0033). The SAM2 producers write `res["particle_id"] = len(records)` (`sam2.py:173`, `:251`) — the index of the row being appended, which renumbers after every drop. One column, two meanings across producers, in a schema ADR-0031 built specifically to stop that (`radius_nm` was the same defect). Found in M6-T05, which needed to link a table row to a particle on screen and used **coordinates** instead (ADR-0065). Fixing it changes what a producer writes into stored tables, so it is a numerical-output change with its own commit, ADR and golden update (ADR-0010) — and the choice is which meaning is right: the prompt's index is more useful, the row counter is what a CSV reader would assume. |
| B-070 | **A ruler cannot be deleted — undo is the only way to remove one** | candidate — needs its own task | `remove_ruler` has existed on the repository since M7-T05 with exactly one caller: `AddRuler.undo`. So a line measured four rulers ago cannot be removed at all, and the only mechanism that reaches it also takes back the four edits made after it. Found by M7-T08's audit, which was looking for tools *missing* undo and found a tool where undo is being asked to do a delete button's job — the workflow ADR-0077 §5 refused to smuggle in. What it needs first is a **ruler selection on the canvas**: annotations got one in M7-T07 (click, thicker outline, an id in the viewmodel) and rulers never did, so there is nothing for a *Delete selected measurement* to act on. Then it is `RemoveRuler` beside `RemoveAnnotation` — restoring the same row, since ADR-0074's `restore_ruler` already exists for the same reason. |
